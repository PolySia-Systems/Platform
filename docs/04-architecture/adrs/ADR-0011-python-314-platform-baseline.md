# ADR-0011: Python 3.14 and Polymarket SDK Baseline

- Status: Accepted
- Date: 2026-07-28
- Last amended: 2026-10-19
- Supersedes: ADR-0005

## Context

Before this decision, PolySia's verified baseline used Python 3.13.14 and
`polymarket-client==0.1.0b11`. The promoted and locked workstation baseline at that decision was
Python 3.14.7. The official Polymarket unified SDK left beta and released
`polymarket-client==0.2.0`. Official stable releases 0.3.0 through 0.7.1 were
subsequently reviewed; 0.7.1 was the previous freeze. The scoped migration
below advances the SDK while retaining the Python baseline.

The existing environment also contained vulnerable `setuptools==82.0.1`.
Project delivery requires a reproducible Windows workstation baseline, a
portable Python dependency lock for Linux deployment, and CI evidence across
the supported Python line. The 2026-08-16 CI optimization decision removes
Python 3.11 and 3.13 support so routine validation can focus on the current
runtime without redundant compatibility jobs.

## Decision

- Support only the CPython 3.14 minor line, expressed as `>=3.14,<3.15` in
  package metadata. Python 3.11 and 3.13 are no longer supported.
- Use CPython 3.14.8 for the explicit Windows bootstrap, CI and container baseline.
  Application metadata remains `>=3.14,<3.15`. Standalone root host utilities
  remain compatible with Ubuntu's Python 3.12+; they do not replace OS Python.
- Configure canonical Linux quality validation for Python 3.14 only. Keep full
  Windows compatibility validation weekly, manually dispatchable, and
  conditional on verified Windows-sensitive changes rather than on ordinary
  pull requests.
- Pin the official unified Polymarket SDK to `0.13.0`.
- Pin direct development tools and the portable transitive lock to versions
  verified by repository quality and supply-chain gates.
- Require `setuptools==84.0.0` in the final pip-managed development
  environment. Retain `setuptools==83.0.0` only as the latest Python 3.14
  bootstrap available from the Conda `defaults` channel; installing the
  portable pip lock deterministically promotes the completed environment to
  `84.0.0`.
- Keep the SDK confined to the existing Polymarket adapter boundary.

No strategy, risk, execution, reconciliation, credential, or live-control
behavior changes as part of this decision.

## 2026-10-19 bounded maintenance decision

Official stable candidates were frozen once at Python 3.15.0 and 3.14.8.
A disposable, resource-capped `python:3.15.0-slim-trixie` binary-only runtime
dependency download failed because locked `pydantic==2.13.5` requires
`pydantic-core==2.46.5`, which had no cp315 wheel. Reproduce with
`python -m pip download --only-binary=:all: -r locks/requirements-runtime-py314.txt`
inside that Python 3.15 image. This is a packaging blocker, not evidence of a
domain defect. Revisit 3.15 when all locked runtime wheels and Linux/Windows
gates are available; no speculative dependency migration is justified here.

The chosen container is `python:3.14.8-slim-trixie` at index digest
`sha256:a2b82f3c48559aa0a8446d9af49826b6e2b2016f4cd2afabfe6013ec53729170`.
The explicit Windows Conda lock was solved against defaults metadata. An isolated
local micromamba materialization did not complete; it does not establish a
successful owner-environment upgrade. Official-Python Windows CI is separate
evidence. No owner Conda environment or shared-host OS Python was changed.

The frozen direct development updates are build 1.6.1, hatchling 1.32.4,
cyclonedx-bom 7.5.0, hypothesis 6.170.1, mypy 2.4.0, pip-tools 7.6.2,
pre-commit 4.7.0 and ruff 0.17.1. Existing explicit lint rules remain enabled;
Ruff's new implicit defaults do not weaken them. Portable transitive pins are
regenerated by the repository lock tool. PR #191 becomes superseded only after
this tested set is integrated. That earlier SDK deferral is superseded by the scoped migration below.

## 2026-10-19 scoped SDK migration decision

The owner authorizes a complete consumed-surface migration to SDK 0.13.0 and a
fresh disabled installation after restoring both hosts. SDK 0.13.0, Pydantic 2.14.1
and core 2.50.1 form the verified v0.4.0 stack; pydantic-settings 2.15.0 and compatible
WebSockets 15.0.1 remain. Only those three runtime pins change. Python stays 3.14.8;
the earlier 3.15 assessment above is historical and was not repeated.

Canonical SDK asset fields remain confined to adapters. A venue-neutral observed
AccountPosition preserves current shares independently from historical volume.
Account pagination fails closed on depth/repetition/incompleteness. The new
indexed approval method is not an on-chain authority or a consumed Platform gate.
Existing signer/funder, order/Risk and Live controls remain. No architecture
replacement, financial schema change, new collector or unused SDK feature is
introduced. [PR #200](https://github.com/PolySia-Systems/Platform/pull/200) owns
actual-SDK deterministic regressions, final matrix and deployment evidence;
[upgrade/rollback guidance](../../10-operations/polymarket-sdk-upgrade.md) records
the exact compatibility and operational boundaries.

## Compatibility and validation

The SDK surface contracts verify the public and secure client methods, order
parameters, signer/private-key and funder/wallet creation inputs, and model
fields consumed by PolySia. The `condition_id` field is explicitly covered
while the deprecated `market` compatibility field remains accepted at the
adapter boundary. The 0.7.1 migration does not adopt new perps, combo RFQ,
scoped session-key, or rate-limit callback capabilities. Tiny Live approved
runtime constants must match the exact pinned SDK version.

Python 3.14 is the only CI target. Python 3.14 wheel installation, CLI smoke,
complete repository validation, strict dependency audit, and SBOM generation
are required before promotion. Removing Python 3.11 and 3.13 is an intentional
compatibility break for environments on those minor versions; it does not
change strategy, risk, execution, reconciliation, credential, or live-control
behavior.

Routine pull requests run lightweight diff, local path/link, Standards, and
secret checks. Executable Python changes add canonical Linux compile, Ruff,
Mypy, complete Pytest, environment-integrity, and applicable locked-wheel
validation. Full Windows compatibility is periodic or Windows-sensitive; it is
not an ordinary pull-request gate. Container and supply-chain gates remain
risk-based, while Windows compatibility and supply-chain validation also run
weekly and on manual dispatch.

This Linux-first policy reflects the controlled Ubuntu/Docker runtime while
retaining evidence for the owner Windows workstation. A Windows-only regression
may be detected by conditional or scheduled validation after an ordinary pull
request has merged. Shared or uncertain CI-control changes fail closed to
comprehensive validation, and an explicit manual full-validation mode remains
available.

## 2026-10-25 bounded validation-policy amendment

CURRENT: one versioned projection in `scripts/classify_ci_changes.py` owns
applicability for CI, scoped/full-local checking and disposable developer packets.
The [validation contract](../../03-requirements/developer-context-packet.md#validation-policy-and-local-preflight)
specifies complete-diff union, conservative fallback, mandatory policy/Gate
contracts, Linux behavior authority and conditional browser/package/image/install
and Windows contexts. Weekly CI is comprehensive; daily trusted-main Windows
health observation reports meaningful failures/partial/overdue evidence without
running or dispatching tests. Full Windows retains duration and JUnit timing output.
No performance saving or future scheduled execution follows from this decision.
Python support, dependencies, Standards pin and trading behavior are unchanged.

## Rollback of the validation-policy amendment

Revert the validation-efficiency merge as one coherent unit so CI, local checker,
packet and Gate remain aligned. Do not reuse release artifacts under a new SHA.

## Earlier policy rollback

Revert the Linux-first CI policy commit to restore Windows quality on relevant
ordinary pull requests and the separate Linux smoke job. Reverting the earlier
2026-08-16 compatibility decision would additionally restore the obsolete
Python 3.11/3.13/3.14 matrix and requires a separate compatibility review.
Never alter signer, funder, wallet, or credential values as part of rollback.
